# Piledriver

Piledriver is a bug-hunting workflow for agents to produce high-quality, tested, and targeted fixes to your code base. It breaks a bug hunt into predefined stages and has the agent walk through those stages with the `piledriver` CLI: recon on the codebase given a general problem area, scoping and assumptions for drawing clear boundaries around the code we're working with, verification (TLA+ model checking, property testing, fuzzing, etc.), writing the bug fix using red/green test-driven methods, and writing a final report.

- **piledriver** (Python CLI) - For agents. Scaffolds sessions, validates phase transitions, runs TLC.
- **pilemonkey** (Go TUI) - For humans. Watch file changes and session progress in real-time.

## Install

```bash
./install.sh
```

This downloads TLA+ tools, installs a `piledriver` symlink into `~/.local/bin` (override with `PILEDRIVER_INSTALL_BIN=/path/to/bin`), installs a Codex `piledriver` skill into `~/.codex/skills/piledriver`, and, if Claude Code is installed, creates the `/piledriver` slash command for Claude Code by copying AGENTS.md.

## Usage
### For the human
From any project directory:

```
/piledriver I think there's a race condition in the session manager
```

With Codex, start by saying something like:

```
Use the piledriver skill to investigate a suspected race condition in the session manager.
```

If you're not using Claude Code/Codex or haven't installed Piledriver as a skill, just point your agent at the AGENTS.md file in this repo. To follow along at a high level with the current phase your agent is in and other status updates, build `pilemonkey` and run the binary from a second terminal in the same directory as Claude Code (currently only compatible with Claude Code). 

### For the agent
Your starting point is AGENTS.md, and your toolkit is the `piledriver` CLI. Here are the important commands you'll be using during the course of the workflow:
```bash
piledriver init <session-name>              # Create session with scaffolding
piledriver set-phase <session> <phase>      # Transition between phases
piledriver technique <session> [type]       # View/set verification technique
piledriver check <session-name> [--sany]    # Run TLC model checker
piledriver tlc <tla> [cfg] [--sany]         # Run TLC on arbitrary .tla/.cfg (no session)
piledriver bug <session-name> <bug-name>    # Create bug reproducer
piledriver test <session-name> [bug-name]   # Run reproducer validation
piledriver pr <session-name>                # Generate PR draft
piledriver status [session-name]            # Show session state
piledriver summary <session> [text]         # View/set task summary
piledriver critique <session> <context>     # Get feedback from critic agent (requires gemini CLI by default)
```

Each command outputs guidance on next steps.

## What it does

1. **Reconnaissance** (optional) - Cast a wide net with race detectors, static analyzers, pattern grep
2. **Scoping** - Define what's formally modeled vs assumed correct
3. **Assumptions** - Document what you assume about components outside the model
4. **Verification** - Write and run the verification (TLA+ has first-class support via `piledriver check`; other techniques are scaffolded and agent-driven)
5. **Testing** - Red/green: commit a failing test that proves the bug, then commit the fix
6. **Report** - Document findings for multiple audiences, generate PR draft

## Directory structure

Created in your project's working directory:

```
.piledriver/
└── <session>/
    ├── state.json          # Phase tracking
    ├── reconnaissance.md   # Automated analysis (optional)
    ├── boundary.md         # What's in/out of the model
    ├── assumptions.md      # Assumptions about "outside"
    ├── model.tla           # TLA+ specification
    ├── model.cfg           # TLC configuration
    ├── probe.md            # Real-world testing plan
    ├── pr-draft.md         # Generated by `piledriver pr`
    └── reproducers/
        └── <bug>/
            ├── README.md
            ├── scenario.yaml  # Config: commits, setup commands
            ├── reproduce.sh   # Test script (exit 0=pass, 1=fail)
            └── results.json   # Generated by piledriver test
```

**Note:** `piledriver init` adds `.piledriver/` to `.git/info/exclude` to keep it out of version control. Some agents (e.g., Gemini) may not show gitignored paths by default—configure your agent to see the directory if needed.

## Usage with other agents

Point your agent at `AGENTS.md` in this repo for workflow instructions. The CLI is agent-agnostic — any tool that can run shell commands can use piledriver.

## Pilemonkey TUI

Run in a second terminal to watch the agent work:

```bash
cd pilemonkey && make && ./bin/pilemonkey -s <session-name>
```

Shows phase progress, file changes, TLC results, and lets you add notes.

## Shell Completion

### Bash

```bash
# Add to ~/.bashrc
source /path/to/piledriver/completions/piledriver.bash

# Or copy to system completions
sudo cp completions/piledriver.bash /etc/bash_completion.d/piledriver
```

### Zsh

```bash
# Copy to a directory in your $fpath
mkdir -p ~/.zsh/completions
cp completions/_piledriver ~/.zsh/completions/

# Add to ~/.zshrc (before compinit)
fpath=(~/.zsh/completions $fpath)
autoload -Uz compinit && compinit
```

### Fish

```bash
# Copy to fish completions directory
cp completions/piledriver.fish ~/.config/fish/completions/
```

## Requirements

- Python 3.9+
- Java (JRE 11+) — `brew install openjdk@17` on macOS

Run `./tools/setup.sh` to check dependencies and download `tla2tools.jar`.

## Configuration

Optional. Create `.piledriver/config.yaml` to customize behavior:

```yaml
critic_command: "gemini -p"  # Command for `piledriver critique` (default: gemini -p)
```

## Reproducer contract

Each reproducer has two files:

**scenario.yaml** - Configuration (you fill this in):
```yaml
base_commit: "abc123"   # Commit where bug exists
fix_commit: "def456"    # Commit with fix (optional)
setup_commands:         # Run after checkout (optional)
  - "go mod tidy"
```

**reproduce.sh** - Test script (you write this):
```bash
#!/bin/bash
# Exit 0 = pass (bug fixed), Exit 1 = fail (bug present)
go test -run TestSpecificCase ./...
```

`piledriver test` handles git operations automatically:
1. Stashes uncommitted changes
2. Checks out base_commit, runs reproduce.sh (should exit 1)
3. Checks out fix_commit, runs reproduce.sh (should exit 0)
4. Restores original git state
5. Writes results.json
